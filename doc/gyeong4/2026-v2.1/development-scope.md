# 경4 프로토콜·메시지 적합성 시험 — 개발 범위 기준

기준일: 2026-09-15 · 작업: **[GM-86](https://app.riido.io/uVml0Nr-7iY91YVOhm8wQ/teams/GM/tasks/vCqzUDgPUEVIeh9wRwZbm)** · 적용 대상: ScenarioEngine의 경4 시험 기능.

## 1. 확정하는 범위

**두 노드 사이의 외부 인터페이스에서 교환되는 프로토콜·메시지와, 이를 시험하는 데 필요한 엔진·상대 모의·관측·판정 기능을 개발한다.**

이는 사용자가 합의한 개발 경계를 구체화한 프로젝트 기준이다. 표준의 연계 목록은 원문대로 보존한다. 기존 A02/A04의 개발 후보 중 DB 어댑터·DB 수집/매핑 개발 제안은 이 기준으로 대체한다. 원래 분석의 사실·질의·PR #1 검토 이력은 유지한다.

| 기준 목록 | 개발 범위 포함 | 개발 범위 제외 | 해석 |
|---|---:|---:|---|
| F2C 9개 | 9 | 0 | 외부 메시지 연계 |
| C2C 21개 | 18 | 3 | UTIC 교통소통·지자체 VDS·스마트교차로 DB 연계 제외 |
| F2F 5개 | 5 | 0 | 외부 메시지 시험 범위에 포함, 시험 접점·전송 프로파일 확인 전 구현 보류 |
| 기본 목록 합계 | **32** | **3** | 본문 상세가 있는 포함 항목 27개 + F2F 5개 |

추가 OID/개념 항목 8개는 별도 대조한다. 내부 개념 연결 1개(IF-G07)는 제외하고, 나머지 7개는 독립 연계 정의와 기존 항목 중복 여부를 확인한다. 이 7개를 32개에 더해 개발 수량으로 확정하지 않는다.

**32는 연계 방향·메시지 목록의 행 수다.** 시험 시나리오·검사 개수, 개발 완료 개수, 즉시 착수 가능한 기능 수를 뜻하지 않는다. 같은 메시지의 송신 SUT와 수신 SUT 시험은 각 역할과 관측 조건에 맞춰 설계한다. F2C/C2C/F2F는 연계 구분으로 유지하고 구현은 통신·변환·검증 패턴에 연결한다.

## 2. 포함 기능과 완료를 입증할 근거

| 포함할 기능 | 개발 내용 | 필요한 관측 근거 |
|---|---|---|
| 외부 통신 절차 | AP-DATEX·MQTT·API·TCP 전문의 적용된 연결·세션·구독·요청/응답·재접속·종료 | 적용 프로파일, 양쪽 역할, 사건 순서, 실제 송수신 기록 |
| 메시지 구문·표현 | 채택된 ASN.1 BER/UPER·V2N 컨테이너·JSON/XML·Binary 구조, 필드 타입/길이·필수 여부 | 원시 바이트와 디코딩값, 참조판, 실패 위치 |
| 의미·프로파일 검증 | 규격의 범위·단위·식별자·필드 관계·TIM 제한속도/차로변경 프로파일 | 규칙 ID/버전, 기대값과 관측값, 조항 근거 |
| 순서·시간·오류·인증 | 명시된 전송 주기/응답시한, 오류 반응, 식별·접속 인증 절차 | 기산점·종료점, 시계/허용오차, 채택된 오류·인증 계약 |
| 시험 상대와 샘플 | 한쪽 SUT를 시험하기 위한 상대 역할·샘플·정상/오류 입력·필요한 시험용 브로커/API 서버 | 제어한 입력, SUT의 외부 반응, 메시지/실행 상관관계 |
| 시험 실행·결과 연결 | 필요한 설정, 시작/중지, 상태·오류 전달, 원시/변환 데이터·판정 결과 표시 | 엔진→시험 모듈→판정 담당→결과 보고 흐름 |
| 우리 시험 도구의 품질·전달 | 영향 검증·회귀, 기존 빌드/패키지·사용 절차의 필요한 보완 | 재현 가능한 실행/빌드 근거와 알려진 제한 |

메시지를 보내는 업무 방향과 TCP client/server, MQTT client/broker, 시험 에이전트/SUT 역할은 각각 기록한다. 브로커가 중간에 있는 MQTT도 외부 연계 범위에 포함한다. 같은 장비·센터 안에 배치된 모듈이라도 별도 SUT 노드와 표준화된 외부 접점이면 배치 위치만으로 제외하지 않는다.

구문 디코딩 성공·소켓 송신 성공·MQTT 발행 완료만으로 SUT의 모든 기능을 통과 처리하지 않는다. 규격이 요구하는 외부 반응을 관측하고, 관측점이나 판정 규칙이 미정이면 해당 조건을 판정 불가로 남긴다. 정상/비정상 입력도 표준 또는 채택된 시험 설계의 근거가 있어야 하며 구현자가 기대 응답을 임의로 정하지 않는다.

## 3. 제외 범위와 경계

아래 DB 제외는 사용자의 명시적 결정이다. 나머지 제외는 위 외부 인터페이스 시험 목적에 따른 **INTERPRETATION / 프로젝트 범위 결정**이다. 표준 자체가 그 기능을 금지하거나 다른 팀의 사업 범위를 삭제한다는 의미로 사용하지 않는다.

| ID | 이번 개발에서 제외 | 경계 안에 남기는 기능 | 근거 |
|---|---|---|---|
| EX01 | DB 연계 3건의 시험 어댑터, 실제 내부 DB 저장·조회·수집·동기화 | 외부 JSON/XML API의 메시지·절차 시험 | 사용자 DB 제외 합의; 제4장 표 4-11/13/14 ↔ 표 4-22/23 |

## 8. 구현 착수와 판정 기준 확정 조건

각 연계는 (1) 송신/수신 SUT와 상대 역할 (2) 실제 시험 접점 (3) 채택 프로토콜·메시지 판 (4) 정상/오류 교환·필드 규칙 (5) 시간/결과 관측점과 기대 반응 (6) 실행 가능한 기준 샘플을 확인한다. 결정된 부분부터 진행하며 미정 규칙을 임의로 통과/실패 기준에 넣지 않는다.
