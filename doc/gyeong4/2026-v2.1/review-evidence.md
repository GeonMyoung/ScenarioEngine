## 3. 수행한 검토와 결과

### 3.1 원문 검토

- SHA-256·크기 재계산: A01에 기록된 원본과 일치. 한글로 내보낸 후에도 원본 해시 유지.
- 기존 텍스트에 빠진 HWP 자동번호를 HWPML의 AUTONUM과 PDF로 보완. 표3-1~6, 표4-1~31, 부록 표 제목을 대조.
- 표3-1/2/3의 목록 행 수 9/21/5, 표3-4/5/6 OID 행 수 6/25/5를 확인.
- 본문 143쪽을 담은 74면 PDF 확인. 본문은 좌우 모아찍기, 부록 일부는 상하 모아찍기, 마지막 p.143은 단독이다. 추출 면의 절반을 쪽 번호로 기계적으로 오인하지 않도록 수정했다.
- 렌더 대조: 체계도p.5, F2C/C2C/F2F목록p.6~9, OID그림p.10·표p.11~12, MQTT역할/시퀀스p.15~16, Binary경로p.105~106, V2N p.136, TIM p.137~143. 상세 필드표는 HWPML의 실제 병합 좌표를 복원해 읽었다.
- OID그림 확대 확인: 표준번호22020은 표의143과 다름. 단순 텍스트 추출로 놓친 값이며 Q06에 추가했다.
- 부록 TIM의 서로 다른 두 표Ⅱ-2, p.16 그림3-3은 원문 표기임을 확인. 자동 번호 누락과 원문 오류를 구분했다.

### 3.3 코드 검토

- category→helper→client1/server3→API집합→UPER변환→웹 판정 응답 경로를 함수 본문으로 추적했다.
- `client1`과 별도 `client1_tr`를 구분했고, payload 검증 함수의 실제 호출(ScenarioClient1.c:1623/1640)을 확인했다.
- 메시지 이름만으로 재사용을 결론내리지 않고 OID·payload·역할과 비교했다.
- prj22 MQTT/REST 비교본의 미커밋 변경과 파일 해시를 기록했다. 해당 작업 트리는 수정하지 않았다.

### 3.4 직접 확인한 수치 사례

- V2N의 고정폭 필드 합은 128bits. 길이 단위/SEM 의미가 없으므로 완성된 wire 총길이 공식으로 승격하지 않았다.
- 표4-28 BSM_INFO의 명시 byte 폭 합은 70(헤더5+본문64+LRC1), 예제 MSGSize70과 일치한다. 다른 전문까지 같은 길이 정의라고 가정하지 않았다.
- 예제 차량번호 `12가3456`은 UTF-8 9bytes, CP949 8bytes. CHAR8의 적용 인코딩이 필요함을 Q19로 기록했다.
- table4-18의 명시 범위·열거 집합과 예제 air-pressure를 비교해 Q15/Q16을 남겼다. 예제를 정답 fixture로 보지 않았다.

## 4. 재검토 방법

1. A01의 파일명·크기·해시로 같은 HWP를 연다. 한글에서 표의 조항·제목·쪽을 확인한다. 예비 텍스트만으로 표 병합/번호를 재판단하지 않는다.
2. OID 사전은 표3-4~6, 메시지 사전은 표4-1~31(Topic표4-2 제외), 필드 사전은 각 표의 행 번호와 대조한다. 반복 인쇄된 header는 원래 표의 새 행으로 세지 않는다.
3. A04의 고정 커밋 링크에서 실제 함수를 읽는다. 그 뒤 `5d29dc2`부터 검토 커밋까지 해당 모듈의 diff를 확인한다.
4. Git 검사: `git diff --check`, PR diff의 파일 목록, 원격 branch SHA와 PR head SHA를 대조한다. 문서 외 파일이 섞이면 제출 범위를 다시 검토한다.
5. 로컬 임시 자료를 사용할 수 있다면 `.local/gyeong4-workplan`의 `tables.json`, `field-records.json`, `document-validation.json`, HWPML/PDF를 참고한다. 이 자료는 표준 전체를 포함하므로 공개 Git에 올리지 않는다.

## 5. 실행하지 않은 검증

빌드·프로그램 테스트·실장비 접속·브로커/API/DB/TCP 통신·지연 측정·웹 검사기 검증·MSI·배포는 실행하지 않았다. 문서 전용 변경이므로 코드 테스트를 추가하거나 과거에 통과한 빌드를 반복하지 않았다. 참조 표준 전체 필드의 채택판 대조와 golden vector 검증도 자료 대기다.
