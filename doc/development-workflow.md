# 작업 창·중앙 검토 창·GitHub·Riido 협업 절차

## 적용 범위

사용자는 각 분석·개발을 서로 다른 Codex 작업 창에서 진행하고,
별도의 중앙 검토 대화에서 완료 보고와 GitHub PR·업데이트를 확인한 뒤
검토·판단하여 Riido에 반영하는 운영 방식을 지정했다.
이 문서는 작업별 직접 Riido 반영 방식에 우선하는 역할 분담이다.
중앙 검토는 사용자가 선택한 15분 간격으로 확인하도록 별도 예약 설정에서 관리한다.
사용자의 현재 요청과 기존 세션의 명시적 제한이 이 절차보다 우선한다.

## 역할

| 역할 | 담당 |
|---|---|
| 작업 창 | Riido 요구사항 조회, 분석·구현·자체 검증, GitHub 브랜치/PR 제출, 검토 자료 보고 |
| 중앙 검토 창 | 완료/업데이트 감지, 실제 결과 검토, 보완·보류·완료 판단, Riido 기록·상태 갱신 |
| GitHub | 코드·분석 문서·변경 이력·PR·검증 근거 |
| Riido | 중앙 검토를 거친 업무 진행·판단·결과와 다음 작업 |

작업 창은 별도 요청이 없는 한 Riido를 읽기 용도로 사용한다.
상태 변경, 완료 처리, 결과 댓글, 신규 업무 등록은 중앙 검토 창에서 수행한다.
작업 창의 자체 검토와 중앙 검토의 판단은 별도로 기록한다.

## 작업 기준과 저장 위치

- 코드·기술 문서·재현 가능한 검증 자료: 현재 `GeonMyoung/ScenarioEngine` 체크아웃.
- 업무 목적·선행 조건·담당·기한·진행 상태·결과 요약: Riido의 `ScenarioEngine` 프로젝트(`GM-60`).
- 현재 Riido 작업공간/팀: `gm` / `gm` (`GM`). 동일 이름의 대상이 있으면 사용자 지시 또는 기존 URL/ID로 식별한다.
- 원본 표준 문서: 사용자가 지정한 자료 위치. 파일명·버전·해시로 분석 기준을 기록한다.
- 다른 PC의 로컬 경로는 달라도 되며, 저장소 내부 절차는 현재 Git 루트를 기준으로 실행한다.
- 원문 HWP/PDF, 개인 설정, 인증 정보는 공개 코드 저장소에 자동 복제하지 않는다. 요청된 코드·문서와 배포 범위를 확인한다.

## 1. 작업을 배정하고 시작할 때

1. 실제 Git 루트, 원격 저장소, 현재 브랜치와 기존 미커밋 변경을 확인한다.
2. 사용자에게 받은 Riido URL/작업 키가 있으면 그 작업과 상위 프로젝트를 조회한다.
   키가 없으면 `ScenarioEngine`의 기존 작업에서 목표·산출물·완료 조건이 맞는 항목을 찾는다.
3. 중앙 검토 창이 업무 연결과 중복 여부를 확인한다. 새 Riido 업무는 사용자 요청 범위와
   기존 마일스톤을 대조해 중앙에서 등록한다. 작업 창은 불명확한 연결을 보고하고 독립적인 검토를 진행한다.
4. 선행 조건, 최신 댓글, 현재 코드와 완료 기준을 대조한다. 미확정 표준 해석은 임의의 판정 규칙으로 굳히지 않는다.
5. 중앙 검토 창은 실제 착수 근거를 확인한 작업만 최신 상태 목록에 따라 `진행 중`으로 갱신한다.
6. 현재 작업 브랜치와 사용자 지시를 우선한다. 새 구현 브랜치는 가능하면 Riido 작업 키를 이름에 포함하고,
   기존 변경을 유지한다. Riido가 반환한 브랜치 이름만을 이유로 요청하지 않은 별도 개발을 시작하지 않는다.
7. 여러 창이 같은 체크아웃의 브랜치나 인덱스를 공유하지 않도록 작업별 Git worktree를 사용한다.
   이미 진행 중인 창의 파일을 임의로 이동·삭제·전환하지 않는다.
8. 중앙에서 새 작업 창을 생성할 때는 작업 ID/호스트, GitHub 저장소·작업 브랜치,
   연결된 Riido 키/ID, 요청 범위를 로컬 조정 목록에 추가한다. 새 Codex 작업 생성은 사용자가 요청한 경우에 한다.

## 2. 진행하는 동안

- 변경은 선택한 업무의 범위로 제한하고 다른 작업의 미완료 내용을 섞지 않는다.
- 분석 보고서, 코드 변경과 검증 자료에 관련 표준·시험 항목·Riido 작업 키를 연결한다.
- 요구사항이나 완료 조건이 바뀌면 작업 창이 변경 이유와 남은 범위를 보고하고 중앙 검토 창이 Riido 반영 여부를 판단한다.
- 작은 문서 변경에 테스트를 추가하지 않는다. 빌드/실행이 필요한 변경은 영향 범위에 맞게 검증하고,
  이미 통과한 검증은 새 변경·실패·미해결 우려가 없으면 반복하지 않는다.
- Riido 또는 GitHub 도구가 제공되지 않아도 가능한 로컬 분석·구현·검증은 계속하고 반영이 남은 부분을 명시한다.

## 3. 작업 창: 자체 검토와 GitHub 제출

1. 실제 diff/산출물을 사용자 요청과 Riido 완료 조건에 대조한다. 범위 누락, 불필요한 변경,
   오류 처리, 호환성, 검증하지 않은 경로를 확인한다.
2. 수행한 검사와 결과를 기록한다. 빌드 성공, 모의 상대 시험, 서버 연계, 실장비 시험,
   다른 실제 PC 확인, MSI 생성과 설치를 서로 구분한다.
3. 요청된 개발 결과의 관련 파일만 커밋하고 작업 브랜치에 push한다.
   commit/PR에는 Riido 작업 키와 문제·변경·검증 근거를 포함한다.
   PR·병합·릴리스·배포는 사용자의 요청 범위와 저장소의 기존 규칙에 맞춰 수행한다.
4. 원격 브랜치/커밋 또는 PR을 조회해 실제 GitHub 반영을 확인한다. 로컬 커밋만 있는 상태를
   GitHub 반영 완료로 보고하지 않는다. 인증 문제를 해결할 때는 요청된 GitHub 계정을 사용한다.

작업 창의 최종 제출에는 Riido 작업별 산출물, 정확한 GitHub 브랜치/PR/커밋,
검증 절차와 결과, 미결정·미완료 사항을 포함한다. Riido 갱신은 중앙 검토를 기다린다.

## 4. 중앙 검토 창: 판단과 Riido 반영

1. 작업 완료 또는 GitHub PR·추가 커밋·검사 결과 변경을 확인한다.
2. 관련 Riido 작업의 최신 완료 조건과 실제 산출물/diff를 대조한다. 필요할 때만 추가 검증한다.
   작업 창이 완료라고 보고했거나 PR이 생성되었다는 사실만으로 완료 처리하지 않는다.
3. 검토 기준 커밋을 기록하고 반영 직전 최신 커밋을 다시 확인한다. 더 최신 변경이 있으면
   과거 커밋에 대한 판단을 최신 결과인 것처럼 반영하지 않는다.
4. 결과를 완료 조건 충족, 보완 필요, 자료/결정 대기로 구분하고 근거와 함께 Riido에 기록한다.
   GitHub 병합·릴리스·배포는 별도 사용자 지시와 기존 승인 범위를 따른다.

중앙 검토 창이 해당 작업에 아래 항목을 결과 댓글로 기록한다.

- 요청/목표와 변경 요약
- GitHub 브랜치·PR·커밋 링크와 정확한 커밋 SHA
- 분석/시험 자료 링크, 실행한 검증과 결과
- 실행하지 않은 검증, 남은 문제와 다음 작업
- 완료 조건별 충족 여부와 상태 변경 결과
- 중앙 검토 판단과 검토한 정확한 리비전

기존 댓글을 먼저 확인해 같은 커밋·결과가 중복 등록되지 않도록 한다.
기술 문서 본문은 Git에서 관리하고 Riido에는 핵심 요약과 해당 버전 링크를 남긴다.
분석 업무처럼 코드 변경이 없는 경우에는 실제 분석 산출물을 근거로 기록하며 불필요한 코드 커밋을 만들지 않는다.

완료 조건을 충족한 작업만 완료로 전환한다. 미실행 시험이나 미확정 요구사항이 완료 조건에 포함되어 있으면
남은 항목을 기록하고 완료로 표시하지 않는다. 외부 반영이 실패하면 실제 상태를 다시 읽어 확인한 후 재시도하며,
중복 생성이나 중복 댓글을 피한다.

## 5. 상태 분류와 현재 확인 사항

상태 이름과 API의 실제 상태 분류를 함께 확인한다. 이름이 `완료`라는 이유만으로 완료로 판단하지 않는다.
상태 변경 후에는 다시 조회해서 의도한 상태와 완료 표시가 반영되었는지 확인한다.

2026-09-15 확인 당시 `gm` 팀의 상태는 다음과 같이 반환되었다.

| 상태 이름 | API 분류 |
|---|---|
| 진행 전 | notStarted |
| 진행 중 | inProgress |
| 완료 | inProgress |
| 완료 (1) | notStarted |
| 취소 | cancelled |

실제 완료 상태 분류가 정리되기 전에는 작업 완료 근거를 댓글로 기록하고,
Riido의 완료 상태 동기화가 남았다고 알린다. 팀 전체 상태 설정을 임의로 바꾸거나 잘못 분류된
`완료` 상태로 전환하지 않는다. 이 표를 영구 상태값으로 사용하지 않고 작업마다 최신 목록을 조회한다.
마일스톤의 상태 변경은 오류가 발생할 수 있으므로 작업(task)의 상태와 상위 단계 요약을 구분한다.

## 6. 사용자에게 보고

작업 창은 제출 자료와 자체 검증 결과를 보고한다. 중앙 검토 창은 검토 판단,
GitHub 링크/커밋, Riido 작업 링크와 실제 반영 상태, 남은 확인 사항을 보고한다.
사용자에게 동일한 반영 지시를 반복 요구하지 않는다.
도구 오류나 실제 의사결정이 필요한 경우에만 무엇이 완료되었고 무엇이 남았는지 구체적으로 설명한다.

## 7. 중앙 확인 주기와 중복 방지

- 사용자 선택 주기: 15분. 중앙 대화에 연결된 heartbeat로 관리한다.
- 로컬 조정 목록: 통합 작업공간의 `.local/coordination/workers.json`.
- 검토 체크포인트: `.local/coordination/review-state.json`.
- 작업 완료/주의 필요와 GitHub PR·등록된 브랜치·main의 새 변경을 확인한다.
- 미검토 변경을 확인하면 필요한 근거를 읽고 Riido 반영까지 수행한 후 체크포인트를 갱신한다.
- 같은 작업 완료, 동일 커밋, 같은 검토 결과를 중복 반영하지 않는다. 외부 요청 결과가 불확실하면 먼저 다시 조회한다.
- 변화가 없거나 이미 알려진 비조치 상태면 조용히 종료한다. 새로운 검토 결과, 실패, 완료,
  사용자 결정이 필요한 변화만 알린다. 알려진 완료 상태 분류 문제를 매 실행마다 반복 알리지 않는다.
- 예약 확인은 앱의 실행 환경에 의존한다. 관련 도구/저장소를 사용할 수 없으면 성공으로 보고하지 않는다.
