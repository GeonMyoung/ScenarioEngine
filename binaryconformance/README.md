# 교차로 상태·TOD TCP Binary 시험

**현행 세션 방식 — BINARY-SESSION-001:** 선택 항목마다 한 번 접속하고 환경설정의 N회 교환을 같은 연결에서 수행한 뒤 연결을 정리한다. 매회 재접속하던 이전 방식은 대체됐다. SeqNo는 회차 사이에도 이어지며 접속 횟수·계획/완료 횟수·세션 정리 결과를 표시한다. 현재 전문 67~72는 별도 조회 요청이 없으므로 제공 측이 송신을 시작하고 명세의 ACK/NACK를 교환한다.

[v5 구현·전체 52항목·실제 웹 검증 결과](../doc/gyeong4/2026-v2.1/binary-single-session-verification-20260925.md). 아래 과거 검증 링크는 당시 회차별 접속 방식의 이력이다.

2026-09-25 확장 완료: [차량운행·최적경로·돌발상황 양측 6개](TRAFFIC.md)를 추가했다. 현재 제3부 표 4-24~4-29의 TCP Binary는 **8개 시나리오·52개 선택 항목**이며 [최종 전체 검증](../doc/gyeong4/2026-v2.1/binary-all-verification-20260925.md)을 완료했다. 아래 설명은 교차로 상태·TOD의 세부 기준이다. 표시 조각은 인코딩 증가분을 고려해 4096바이트로 조정했고 Binary 알림을 별도 작업자에서 순서대로 전달한다.

제3부 표 4-24~4-26의 업무 데이터와 경6 인터페이스 설계서 §4·§6.8~6.10을 적용한 양측 개발 시험이다. 제4부 제4장 4.1.1의 정보제공·수신 결과 회신을 연결하되, 문서에서 미정인 규칙은 **BINARY-SIGNAL-001 개발 기준**으로 표시한다. 실제 장비의 상호운용이나 미확정 계약의 승인을 뜻하지 않는다.

| 설계 / 등록 | 시험 이름 | 시험 시스템 | 시험 대상 | case |
|---|---|---|---|---|
| SC14 / 68 | 통합교통관제시스템 대상 교차로 상태·TOD 정보수신 시험 | 신호제어서버 TCP Server | 통합교통관제시스템 TCP Client | `signalServer2center_binary_v1` |
| SC35 / 69 | 신호운영시스템 대상 교차로 상태·TOD 정보제공 시험 | 통합교통관제시스템 TCP Client | 신호제어서버 TCP Server | `centerClient2signal_binary_v1` |

구분 C2C. 업무 정보는 신호운영시스템 → 통합교통관제시스템, ACK/NACK는 반대 방향이다. 별도 정보요청 전문을 만들어 전송하지 않는다.

## 데이터·프레임

| 정보 | 메시지 번호 | 레코드 크기 | 기본 1레코드 프레임 |
|---|---:|---:|---:|
| INT_ALL_STATUS | 68 | 386바이트 | 392바이트 |
| INT_ALTER_STATUS | 69 | 386바이트 | 392바이트 |
| INT_TOD_INFO | 70 | 42바이트 | 48바이트 |

- Big-Endian. 정보 프레임은 메시지번호 1 + 전체 SIZE 2 + Start-End 1 + SeqNo 1 + 데이터 + LRC 1바이트다.
- 상태정보 LC_NO는 **표준의 1바이트**다. 설계서의 4바이트 레코드로 자동 전환하지 않는다. LC_TYPE도 표준의 숫자 1바이트로 해석한다. TOD의 LC_NO는 표준의 4바이트다.
- 상태정보의 LC_NAME은 100바이트, 각 좌표 문자열은 20바이트다. 바이트 폭과 선택한 인코딩·패딩을 검사한다. 표준에 없는 좌표 숫자 범위, LC_STATUS 코드 상한, LC_TYPE 문자 변환을 추가하지 않는다.
- TOD 시작시·분은 0~23/0~59, 주기·옵셋·현시 값은 2바이트 폭을 적용한다. 수치는 비부호 Big-Endian으로 해석하는 채택 기준이며 부호 규칙이 공식 확정된 것으로 주장하지 않는다.
- 복수 레코드는 고정 크기 레코드를 연속 배치한다. 복수 교차로 시험에서는 서로 다른 LC_NO가 최소 2개여야 한다.
- ACK/NACK는 메시지번호 1 + SIZE=5의 2바이트 + SeqNo 1 + 결과 1바이트다. 결과 1=ACK, 0=NACK이며 Start-End/LRC는 없다.
- TCP의 부분 수신·합쳐진 수신과 정보의 논리적 분할을 구분한다. TCP는 SIZE만큼 누적 수신하며, 논리적 분할은 Start(0)→End(1)의 두 프레임을 지원한다. 단독 프레임은 2다.

## 미정 운용 규칙의 설정

| 설정 | 기본값 | 의미·한계 |
|---|---|---|
| lrc_mode | xor8 | 초기값 0, 메시지번호부터 데이터 끝까지 XOR. sum8 선택 시 합의 2의 보수. 계산식은 문서 미명시 개발 기준이다. |
| ack_seq_mode | echo | 원송신 SeqNo 대응. fixed1 선택 시 1 고정. 원문의 `1`이 값인지 폭인지는 미확정이다. |
| char_encoding | UTF-8 | CP949 선택 가능. CHAR는 NUL 패딩, 값은 비어 있지 않게 준비한다. 자동 인코딩 추정은 하지 않는다. |
| first_sequence | 0 | 프레임별 0~255 순환, 연결마다 재시작하는 개발 기준이다. |
| heartbeat_ack | true | TOD Heartbeat에도 ACK를 사용한다. 미사용 설정도 검증했다. 공식 필수 여부는 미정이다. |
| heartbeat_period_ms | 60000 | 설계서의 1분. 다른 값으로 실행하면 `standardHeartbeatTiming=false`로 기록한다. |
| heartbeat_tolerance_ms | 1000 | 측정 환경 허용오차이며 표준 규정의 허용오차는 아니다. |
| heartbeat_samples | 2 | 추가 운용 검증의 Heartbeat 횟수. 업무 정보교환의 최소 10회를 대체하지 않는다. |

TOD Heartbeat는 데이터 없는 메시지 70의 6바이트 공통 프레임을 채택했다. §6.10은 주기를 설명하고 §6.11~6.12는 빈 헤더 형태를 설명하므로, TOD의 구체적 형태·응답 적용은 후속 확인 대상이다. 중간 분할 프레임 값이 미정이어서 3개 이상 논리 분할 그룹은 추가하지 않았다.

## 선택 항목

| 항목 | 신호운영시스템 제공 대상 | 통합교통관제시스템 수신 대상 | 반복 |
|---|---|---|---|
| 전체 교차로 상태 | 제공 프레임 검사 후 ACK | 유효 프레임 제공 후 ACK 확인 | 10회 이상 |
| 변경 교차로 상태 | 전체 상태 준비 후 변경 정보 검사·ACK | 전체 상태 제공 후 다른 상태 제공·ACK 확인 | 10회 이상 |
| TOD | 제공 프레임 검사 후 ACK | 유효 TOD 제공 후 ACK 확인 | 10회 이상 |
| 분할 상태 [추가] | Start/End 조립·SeqNo 확인 | 두 프레임 제공·각 ACK 확인 | 10회 이상 |
| 복수 교차로 [추가] | 서로 다른 교차로 2개 이상 확인 | 복수 교차로 제공·ACK 확인 | 10회 이상 |
| TOD Heartbeat [추가] | 실제 수신 주기·빈 프레임 확인 | 주기적 제공 및 선택한 ACK 확인 | 기본 2회 |
| LRC 오류 거부 [추가] | — | 잘못된 LRC 제공 후 NACK 확인 | 10회 이상 |
| 데이터 길이 오류 거부 [추가] | — | 유효 LRC지만 레코드 폭이 잘못된 정보의 NACK 확인 | 10회 이상 |
| 순서번호 오류 거부 [추가] | — | 정상 Start 뒤 잘못된 SeqNo의 End에 대한 NACK 확인 | 10회 이상 |

SC35는 6항목, SC14는 9항목이다. SC14는 사용자가 요청한 양측 범위의 추가 수신 설계이며 제4부에 별도 수신시험이 있다고 표시하지 않는다. 정보제공 시험도 원문의 요청 메시지 대신 연결·변경 사건을 자극으로 사용하므로 원 시험방법 전체를 그대로 구현했다는 의미로 확대하지 않는다.

전체 상태·TOD도 한 연결에서 N회 정보와 수신 응답을 교환한다. 변경정보의 기준 자료는 접속 후 한 번 준비하고 N회의 후속 변경정보를 검사한다. 준비 자료는 N회에 포함하지 않는다. 최초 수신 제한시간(기본 1000ms)은 첫 정보에 적용하며 이후에는 수신 제한시간을 적용한다. 실제 시험 환경은 해당 자료를 반복 제공할 수 있도록 준비해야 한다. 원천 사건 발생시각을 직접 알지 못한 수신으로 사건→제공 1초를 입증하지 않는다.

분할 순서번호 오류의 추가 시험은 NACK 확인 후 정상 순서번호의 끝 프레임을 다시 보내 기존 조립을 마친 뒤 다음 오류 회차를 진행한다. 이 복구 교환은 추가 시험의 채택 절차이며 공통 규격의 재전송 의무로 표시하지 않는다. 실제 단절·실패·사용자 중지는 완료 횟수를 보존하고 세션을 정리한다.

## 실행·증거

- [registration](registration/)의 tsb와 example.json을 사용한다. SC14는 시험기가 수신 대기하고 대상 클라이언트가 접속한다. SC35는 대상 서버를 먼저 실행하고 시험기가 접속한다. IPv4 접점을 사용한다.
- 에뮬레이터 `emulator/signal_sut.py`의 `--role receiver`는 경4 수신측, `--role provider`는 경6 제공측이다. `--config`에는 시험 선택과 운용 설정, `--output`에는 새 증적 폴더, `--run-manifest`에는 엔진 작업 폴더의 `binary-run.json` 경로를 준다.
- `binary-run.json`은 개발 검증의 실행 식별을 연결하는 로컬 계측 자료다. TCP에 테스트용 헤더나 가상의 조회 전문을 추가한 것이 아니다. 실제 SUT가 이 파일을 지원해야 하는 규격으로 제시하지 않는다.
- 에뮬레이터는 설정된 항목 순서에 맞춰 초기 자료·변경 사건·오류를 준비한다. 여러 실제 정보가 섞여 오는 운영 스트림을 자동 분류하는 범용 수집기는 아니다. 시험 대상의 제공 정보를 해당 항목에 맞춰 준비한다.
- 모든 정보 프레임·분할·Heartbeat·ACK/NACK의 HEX 원문, 방향, 회차, 해석 결과를 표시·저장한다. 분할은 조립 결과도 추가한다. 부분 수신·부분 전송은 별도로 표시하며, 바이트가 없으면 메시지를 만들어 채우지 않는다.
- 엔진은 직접 관측한 송수신·형식·수신 응답·타이밍을 판정한다. ACK를 내부 업무 반영 로그의 직접 관측으로 표현하지 않는다. 개발 검증에서는 `tools/review_evidence.py`로 양측 원문과 처리 기록도 대조한다.
- 상세 상태 START→SUCCESS/FAIL/STOPPED, 전체 MainScenario 결과 뒤 FINISH 1회. COMPLETE 미사용. 실패 이후 항목은 미실행으로 남긴다.
