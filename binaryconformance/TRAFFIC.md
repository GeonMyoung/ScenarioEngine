# 차량운행·최적경로·돌발상황 TCP Binary 시험

**현행 반복 방식:** 선택 항목마다 한 TCP 세션에서 환경설정 횟수만큼 교환하고 연결을 정리한다. 요청 전문이 없는 현재 연계는 데이터 제공 측이 전송을 시작하며 ACK/NACK를 유지한다. 변경정보의 최초 기준 자료는 준비 회차로 구분한다. [BINARY-SESSION-001 및 세션 동작](README.md)을 적용한다.

제3부 표 4-27~4-29의 데이터 정의와 경6 설계서 §4·§6.7·§6.11·§6.12의 접속·전송 규칙을 적용한다. 기존 [교차로 상태·TOD](README.md)의 공통 통신 기능을 재사용한다. 미정 규칙은 BINARY-TRAFFIC-001 개발 기준으로 구분한다.

## 데이터 적용

### 차량운행정보: BSM_INFO

레코드 64바이트, 한 레코드의 전체 프레임은 70바이트다.

| 필드 | 정의 |
|---|---|
| CREDATE | CHAR 8, 표준 예시에 따라 YYYYMMDD 채택 |
| VEH_ID / VEH_NO | CHAR 16 / CHAR 8 |
| LONGITUDE / LATITUDE | DOUBLE 각 8 |
| ALTITUDE / ANGLE / SPEED | FLOAT 각 4 |
| GEAR | CHAR 4 |

FLOAT/DOUBLE은 IEEE 754 Big-Endian, 유한값을 채택한다. 숫자 문자열·boolean을 숫자로 변환하지 않는다. FLOAT 범위 초과·0으로 소실되는 입력 및 수신 NaN/Infinity를 거부한다. IEEE 직렬화 후 실제 값으로 원문·해석 결과를 대조한다. 표준에 없는 지리적 범위나 속도·헤딩 범위를 임의로 추가하지 않는다.

설계서의 8바이트 수집일시 예시는 전체 날짜·시각이어서 의미가 미정이다. epoch 정수로 바꾸지 않고 표준 CHAR8을 적용한다. GEAR도 설계서의 BYTE로 바꾸지 않는다. 표준 예시의 `12가3456`은 UTF-8에서 9바이트, CP949에서 8바이트다. 기본 UTF-8 시험자료는 ASCII 차량번호를 사용하며 CP949의 한글 예시도 별도로 검증했다.

### 최적경로정보: OPTIONAL_ROUTE

- 공통부: 년 2 + 월/일/시/분/초 각 1 + lot/lat DOUBLE 각 8 + indivAdIdNo 1 = 24바이트.
- 차량별: indivAdId CHAR10 + linkId CHAR10 + linkPos INTEGER3 + linkInfoType INTEGER1 + viaLinkNo INTEGER1 = 25바이트.
- 경유 항목별: **viaLinkSeq INTEGER20 + viaLinkId CHAR3 + viaLinkTurn INTEGER1 = 24바이트**.
- 표준의 차량 수·경유 수와 실제 반복 개수를 정확히 대조한다. 부족하거나 남는 바이트를 거부한다. 설계서의 Belt 문자열·21바이트 반복으로 자동 전환하지 않는다.

20바이트 순번은 0~2^160-1의 비부호 Big-Endian으로 채택한다. 전송 타입을 CHAR로 변경한 것이 아니다. **화면·JSON 증적에서는 정밀도 손실을 막기 위해 해당 정수를 10진 문자열로 표시**하며 프레임 SeqNo(1바이트)와 구분한다. 최대값의 실제 송수신·화면·보고서 보존을 검증했다.

표시 자료는 공통 레코드 1개 아래 `pol6IndivAdInfoDtoList`, 각 차량 아래 `pol6RouteIntoDtoList` 배열을 사용한다. 이름은 표준 정의표를 따랐으며 예시의 다른 철자와 혼용하지 않는다. 이 JSON은 Binary 해석 표시 형식이다.

### 돌발상황정보: INC_INFO

고정 612바이트 + LINK_COUNT 1바이트 + 링크별 CHAR10이다. 두 링크의 단일 레코드는 633바이트, 전체 프레임은 639바이트다. 여러 이벤트는 레코드를 연속 배치하는 개발 기준을 적용한다.

EVENT_ID 18, EVENT_NM 500, INC_TY 2, INC_DTL_TY 4, OCRN_DT/END_DT 각 14, OCRN_LOT/OCRN_LAT 각 20, OCRN_LINK_ID 10, CNTRL_TY 1, PRGRS_STTS 2바이트를 따른다. EVENT_NM은 설계서가 명시한 NULL 종료가 500바이트 안에 있어야 한다. 따라서 실제 텍스트 최대는 499바이트다.

년·월·일·시·분·초 및 날짜 문자열의 유효성을 검사한다. END_DT의 `00000000000000`은 표준 예시의 종료 미정 값으로 허용한다. 표준 예시의 유형 `01`/세부유형 `0101`을 설계서의 다른 코드표로 자동 수정하지 않으며 코드 목록의 적용 차이는 이슈로 남긴다.

## 선택 항목·시간·판정

BSM 제공측은 정상·1초 주기·분할·복수 차량 4항목, 수신측은 이에 LRC/데이터 길이/순서번호 오류 거부를 더한 7항목이다. 최적경로·돌발상황은 정상·사건에 따른 변경·분할·복수 자료·자료 없음 Heartbeat의 제공 5항목, 수신측은 오류 거부 3개를 더한 8항목이다.

- 항목당 10회 이상. BSM 주기는 같은 연결에서 10개 정보를 확인하여 9개 간격을 측정한다. 기본 1000ms, 허용오차 200ms는 시험 환경값이다.
- 변경 조건은 같은 연결에서 변경 전 자료와 달라진 자료를 확인한다. 원천 사건 발생 시각을 관측하지 않았다면 발생→제공 지연을 입증했다고 표시하지 않는다.
- 최적경로·돌발상황 자료 없음은 최초 연결 후 **데이터 없는 해당 메시지의 6바이트 Heartbeat**를 확인한다. 미정 주기를 TOD의 60초와 동일하다고 가정하지 않는다.
- 정상·분할·복수·자료 없음은 접속별 단일 교환을 반복한다. 복수 BSM은 서로 다른 VEH_ID, 복수 최적경로는 서로 다른 indivAdId, 복수 돌발상황은 서로 다른 EVENT_ID를 요구한다.
- 수신측은 채택 기준에 맞는 ACK/NACK를 관측한다. 제공측은 표준 데이터 검사 후 결과를 회신한다. 내부 업무 처리 로그를 직접 관측한 것으로 확대하지 않는다.

## 전체 자료 표시와 전달

긴 프레임 원문·해석 자료·조립 결과는 전부 보존한다. 원문 HEX, 회차, 방향, 프레임 순번과 표시 분할 번호를 함께 남긴다. 표시용 JSON 분할은 TCP의 Start-End 분할과 별개다.

검증 중 알림이 한꺼번에 호스트 대기열에 들어가 WebSocket 송수신 완료 처리가 지연되는 현상을 확인했다. Binary 모듈에 전용 순차 전달 작업자를 두어 호스트의 처리 완료를 확인한 후 다음 알림을 전달하도록 보완했다. 시험 통신은 별도로 진행한다. JSON/Base64의 크기 증가도 고려하여 표시 조각은 4096바이트로 나누고 작은 자료는 직접 보낸다.

모든 알림을 순서대로 전달한 뒤 MainScenario FINISH가 처리된다. 사용자 중지는 호스트가 호출한 중지 명령을 알림 작업자가 다시 기다리는 교착을 피하도록 구성했다. `binary-delivery.json`에 처리·대기·폐기·오류 건수를 기록하며, 호스트 처리 완료와 서버의 수신 확인은 검증 단계에서 구분해 대조한다.

`COMPLETE`는 사용하지 않는다. 상태는 START→SUCCESS/FAIL/STOPPED, 전체 FINISH 1회다. 제공·수신 역할과 원천 자료 준비 방법은 등록 설명 및 case별 [설정 예제](registration/)를 따른다. 에뮬레이터·코덱·검토 도구 실행법은 [공통 안내](README.md)에 있다.
